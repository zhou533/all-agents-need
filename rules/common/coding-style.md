# 编码风格

## 不可变性（关键）

始终创建新对象，绝不改变现有对象：

```
// Pseudocode
WRONG:  modify(original, field, value) → changes original in-place
CORRECT: update(original, field, value) → returns new copy with change
```

理由：不可变数据可以防止隐藏的副作用，使调试更容易，并支持安全的并发。

## 核心原则

### KISS（保持简单）

- 优先选择真正可行的最简单方案
- 避免过早优化
- 为清晰而非聪明进行优化

### DRY（不要重复自己）

- 将重复逻辑抽取到共享函数或工具中
- 避免复制粘贴导致的实现漂移
- 只在重复真实发生时引入抽象，不要凭空预判

### YAGNI（你不会需要它）

- 不要在真正需要之前就构建功能或抽象
- 避免臆测性的通用化
- 从简单开始，当压力真实出现时再重构

## 文件组织

多个小文件 > 少数大文件：

* 高内聚，低耦合
* 通常 200-400 行，最多 800 行
* 从大型模块中提取实用工具
* 按功能/领域组织，而不是按类型组织

## 错误处理

始终全面处理错误：

* 在每个层级明确处理错误
* 在面向用户的代码中提供用户友好的错误消息
* 在服务器端记录详细的错误上下文
* 绝不默默地忽略错误

## 输入验证

始终在系统边界处进行验证：

* 在处理前验证所有用户输入
* 在可用时使用基于模式的验证
* 快速失败并提供清晰的错误消息
* 绝不信任外部数据（API 响应、用户输入、文件内容）

## 命名约定

- 变量与函数：`camelCase`，使用描述性命名
- 布尔值：优先使用 `is`、`has`、`should`、`can` 前缀
- 接口、类型、组件：`PascalCase`
- 常量：`UPPER_SNAKE_CASE`
- 自定义 hooks：`camelCase` 并加 `use` 前缀

## 需要避免的代码坏味道

### 深度嵌套

一旦逻辑开始堆叠，优先使用早返回而非嵌套条件。

### 魔法数字

为有意义的阈值、延迟和限制使用命名常量。

### 长函数

将大函数拆分为职责清晰的聚焦片段。

## 代码质量检查清单

在标记工作完成之前：

* \[ ] 代码可读且命名良好
* \[ ] 函数短小（<50 行）
* \[ ] 文件专注（<800 行）
* \[ ] 没有深度嵌套（>4 层）
* \[ ] 正确的错误处理
* \[ ] 没有硬编码的值（使用常量或配置）
* \[ ] 没有突变（使用不可变模式）
